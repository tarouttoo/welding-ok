# Контракт `ok.json`

Нормативная спецификация содержимого ОК без оформления (ADR 0001): агент
производит `ok.json`, линтер и рендерер потребляют его. Валидатор структуры —
`contract/ok_schema.py`, CLI — `contract/validate_ok.py`, тесты и минимальный
синтетический пример — рядом. Термины — по [`GLOSSARY.md`](../GLOSSARY.md).

## Язык ключей и значений

**Ключи — латиница в `snake_case`, значения — русский.** Ключи принадлежат
коду и никогда не попадают в документ; значения, которые переносятся в ОК, —
русские, терминология ГОСТ сохраняется. Решение фиксируется этой строкой и
меняется только правкой всего контракта разом.

## Верхний уровень

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `product` | object | Изделие: метаданные продукта. |
| `documents` | array | Список ОК. Форма — список, чтобы многооперационные ОК позже не потребовали переделки рендерера. **v1: ровно один документ** (одна ОК на изделие). |

### `product`

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `name` | string | Наименование изделия. |
| `material` | string | Марка материала (v1: `ст3`, `09Г2С`; контроль марки — не здесь, см. «Граница ответственности»). |
| `process` | string | Способ сварки. **v1: только `"РД"`.** |

## Документ (`documents[i]`)

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `operations` | array | Операции документа, минимум одна. Нумерация строго монотонна (см. ниже). |
| `assumptions` | array of string | Спорные решения, вынесенные агентом. Обязательное поле, может быть пустым: черновик всегда полный. |

## Операция (`operations[i]`)

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `number` | integer ≥ 1 | Номер операции. Внутри документа номера **строго возрастают**; непрерывность (1, 2, 3…) не требуется. |
| `position` | string | Положение сварки (например «нижнее»). Значение выбирается агентом по файлам знаний. |
| `equipment` | object | Оборудование. v1: ровно `{"electrode_type": "УОНИ-13/55"}` — другое значение валидатор не пропустит. |
| `params` | object | Режимы сварки (см. ниже). |
| `welds` | array of string | Швы, закрываемые операцией, по нумерации чертежа: `Ш1`, `Ш2`, … Каждый шов закрывается ровно одной операцией документа; повторов внутри списка нет. |
| `sketch_refs` | array of string | Заглушки-ссылки на эскизы КЭ: `КЭ1`, `КЭ2`, … Сам эскиз выполняется вручную и в систему не входит. |
| `transitions` | array | Переходы операции, минимум один. |

### `params` (режимы)

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `current_type` | string | Род тока: `"постоянный"` или `"переменный"`. |
| `current_a` | number > 0 | Величина тока, А. |
| `polarity` | string | Полярность: `"прямая"` или `"обратная"`. Обязательна при `"постоянный"`; при `"переменный"` поле отсутствует (полярность задаётся только для постоянного тока). |
| `electrode_diameter_mm` | number > 0 | Диаметр электрода, мм. |
| `pass_count` | integer ≥ 1 | Число проходов. |

Допустимые сочетания режимов (ток/диаметр/проходы для толщины и марки) —
инженерное знание: его задают файлы знаний и проверяет линтер, а не валидатор
структуры.

## Переход (`transitions[i]`)

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `number` | integer ≥ 1 | Номер перехода. Внутри операции номера строго возрастают. |
| `description` | string | Содержание перехода — текст, переносящийся в ОК. |

## Граница ответственности

Проверяет **валидатор контракта** (этот модуль) — всё, что не требует брифа:
структура и типы полей, шаблоны значений (`Ш<n>`, `КЭ<n>`), строгая
монотонность номеров операций и переходов, уникальность швов (шов закрывается
ровно одной операцией), род тока ↔ полярность, v1-ограничения (процесс `РД`,
электрод `УОНИ-13/55`, один документ).

Остаётся **линтеру** — сверка с брифом: каждый шов брифа покрыт операцией,
марка материала в диапазоне v1, реалистичность режимов.

**Рендерер** ничего не проверяет и не решает: он только оформляет валидный
контракт по ГОСТ 3.1118-82 / ГОСТ 3.1404-86 (ADR 0001). Отображение полей в
графы формы — предмет задачи рендерера; контракт полям её не предрешает.

## CLI

```
python3 contract/validate_ok.py examples/minimal/ok.json
```

Коды возврата: `0` — валиден; `1` — невалиден или файл не разбирается как JSON
(все ошибки построчно в виде `error: <путь>: <сообщение>`, путь в стиле
`documents[0].operations[1].welds[2]`); `2` — ошибка вызова или чтения файла.

## Пример

[`examples/minimal/ok.json`](../examples/minimal/ok.json) — минимальный
синтетический пример (ADR 0002, выдуманное изделие): проходит валидацию и
round-trip. Каноническая форма файла — `json.dumps(..., ensure_ascii=False,
indent=2)` с переводом строки в конце; тесты
(`contract/test_ok_contract.py`, `python3 -m pytest`) проверяют и это.

## Расширение v1

Новое расширение (второй документ в `documents`, новый электрод или процесс,
новое поле) — сознательная правка контракта: правится валидатор, этот
документ и пример. Заменой файлов знаний это не делается: файлы знаний
наполняют поля изнутри, контракт задаёт их снаружи.
